# Prototype

A prototype is **throwaway code that answers a question**. The question decides the shape.

In Rio, keep the experiment isolated from production code, meeting history, and live services; use synthetic content. Browser demos are local design artifacts, not native-app verification. Record the question and result in `docs/research` or the relevant `docs/specs` file. Production adoption follows `/spec`, `/plan`, `/build`, and `/review`, including regression tests. Native interactive validation belongs to the primary agent and requires the signed installation flow when the owner requests it.

## Pick a branch

Identify which question is being answered — from the user's prompt, the surrounding code, or by asking if the user is around:

- **"Does this logic / state model feel right?"** → [LOGIC.md](LOGIC.md). Build a single shareable HTML file — free-play buttons plus tabbed guided walkthroughs — that pushes the state machine through cases that are hard to reason about on paper, and that a non-developer can drive.
- **"What should this look like?"** → [UI.md](UI.md). Generate several radically different UI variations on a single route, switchable via a URL search param and a floating bottom bar.

The two branches produce very different artifacts — getting this wrong wastes the whole prototype. If the question is genuinely ambiguous and the user isn't reachable, default to whichever branch better matches the surrounding code (a backend module → logic; a page or component → UI) and state the assumption at the top of the prototype.

## Rules that apply to both

1. **Throwaway from day one, and clearly marked as such.** Use an explicitly named local prototype artifact outside the production target, with a pointer to the module or screen it explores.
2. **Trivial to run.** A UI prototype starts from one command in the project's task runner — `pnpm <name>`, `python <path>`, `bun <path>`, etc. A logic demo is a single HTML file the user double-clicks. Either way, no thinking required to start it.
3. **No persistence by default.** State lives in memory. Persistence is the thing the prototype is _checking_, not something it should depend on. If the question explicitly involves a database, hit a scratch DB or a local file with a clear "PROTOTYPE — wipe me" name.
4. **Skip the polish for isolated throwaway artifacts.** Keep only the handling needed to run the experiment. Production behavior changes still require the project's regression tests and checks.
5. **Surface the state.** After every action (logic) or on every variant switch (UI), print or render the full relevant state so the user can see what changed.
6. **Capture it when done.** Record the verdict, question, and artifact location in `docs/research` or the relevant spec. Keep the artifact local and uncommitted unless retaining it in the repository is part of the agreed scope. Any commit goes through `/review` on `main`; production implementation starts through the factory lifecycle.
